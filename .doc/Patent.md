## 발명의 명칭

**비중앙화 멀티 스토리지 이벤트 기반 분산 RAG/LLM 플랫폼 및 그 운용 방법**

(Non-Centralized Multi-Storage Event-Driven Distributed RAG/LLM Platform and Operation Method Thereof)

---

## 기술분야

본 발명은 클라우드 및 온프레미스 환경에 분산된 복수의 문서 스토리지에서 발생하는 이벤트를 수신하고, 문서를 중앙 서버에 집중하지 않으면서 정책 기반으로 분산 인덱싱 및 질의 라우팅을 수행하여 RAG(Retrieval-Augmented Generation)/LLM(Large Language Model) 기반 문서 질의응답 서비스를 제공하는 플랫폼 및 그 운용 방법에 관한 것이다.

---

## 배경기술

### 종래 기술의 문제점

**[0001]** 기존의 문서 관리 및 RAG/LLM 서비스는 다음과 같은 구조적 한계를 가진다.

**[0002]** 첫째, 문서 중앙화 의존성: 기존 RAG 시스템은 AWS S3, GCP Storage, Azure Blob 등 다양한 스토리지에 산재한 문서를 중앙 수집 서버로 가져와 임베딩·인덱싱을 수행한다. 이는 대용량 문서 전송에 따른 네트워크 부하, 보안 규정(데이터 주권, GDPR 등) 위반 위험, 문서 중복 저장에 의한 스토리지 낭비를 초래한다. (참조: KR101304452B1, KR20180017470A)

**[0003]** 둘째, 정적 인덱싱 전략: 종래 RAG 시스템은 벡터 임베딩(Vector Embedding) 방식 또는 Vectorless 방식 중 하나를 고정적으로 사용한다. 문서의 보안 등급, 크기, 참조 빈도, 접근 권한 등 동적 속성에 따라 인덱싱 전략을 자동으로 결정하는 정책 엔진이 부재하다. (참조: WO2025239566A1, WO2026014800A1)

**[0004]** 셋째, 단일 모델 의존: 기존 시스템은 특정 상용 LLM 또는 오픈소스 LLM에 고정되어, 문서의 보안 등급·소재 위치·사용자 프로파일에 따른 동적 모델 선택이 불가능하다. (참조: WO2025110708A2)

**[0005]** 넷째, 이벤트 처리 비효율: 스토리지에서 발생하는 문서 신규/수정/삭제 이벤트를 단순 선입선출(FIFO) 방식으로 처리하여, 자주 참조되는 중요 문서의 인덱싱 지연이 발생한다.

## 발명의 상세한 설명

### 발명의 목적

**[0010]** 본 발명은 다음을 달성하는 것을 목적으로 한다.

- 복수의 이기종 클라우드/온프레미스 스토리지에서 문서를 중앙에 집중하지 않고 분산 인덱싱을 수행하는 비중앙화 아키텍처 제공
- 문서 메타데이터(보안 등급, 조직, 규제, 사용 이력)를 기반으로 인덱싱 방식·위치·LLM을 자동 결정하는 정책 엔진 구현
- Vector 인덱싱과 Vectorless 인덱싱을 이벤트 기반으로 동적 전환·조합하는 하이브리드 인덱스 전략 제공
- 문서 참조 빈도 및 질의 로그를 반영한 우선순위 기반 증분 인덱싱 큐 운용
- 사용자 질의 유형·프로파일·보안 맥락에 따른 멀티 LLM 동적 오케스트레이션

#### 2. 핵심 구성요소 상세 설명

**[0020] 로컬 인덱싱 에이전트 (Local Indexing Agent)**

각 스토리지에 배치되는 에이전트로, 다음 기능을 수행한다.

- 스토리지 네이티브 이벤트 수신: S3 Event Notification, GCS Object Notifications, Azure Event Grid, FileSystem Watcher (inotify) 등
- 문서 메타데이터 추출: 문서 유형, 크기, 보안 등급 태그, 조직 정보, 생성/수정 시각
- 중앙 이벤트 허브로 "요약 이벤트" 전송: **문서 원본 콘텐츠는 중앙으로 전송하지 않음**
- 정책 엔진의 인덱싱 지시를 수신하여 로컬에서 직접 인덱싱 수행

```
요약 이벤트 구조:
{
  event_type: "CREATE" | "UPDATE" | "DELETE",
  storage_id: "aws-s3-prod-bucket",
  document_id: "path/to/document.pdf",
  metadata: {
    size_bytes: 1048576,
    security_level: "CONFIDENTIAL",
    org_unit: "R&D",
    jurisdiction: "KR",
    content_type: "application/pdf",
    tags: ["manual", "process"]
  },
  timestamp: "2026-04-30T09:00:00Z"
}
```

**[0030] 정책 엔진 (Policy Engine)** — 핵심 발명 포인트 ①

정책 엔진은 이벤트 수신 시 다음 속성을 종합하여 인덱싱 전략을 자동 결정한다.

| 입력 속성 | 설명 |
|---------|-----|
| 보안 등급 | OPEN / INTERNAL / CONFIDENTIAL / SECRET |
| 규제/관할권 | GDPR, PIPA, 데이터 주권 (KR, EU, US 등) |
| 조직 단위 | 부서/프로젝트/팀 |
| 문서 크기 | 청킹 전략 결정 기준 |
| 참조 빈도 | 과거 질의 로그 기반 인기도 점수 |
| 이벤트 유형 | 신규/수정/삭제 |

정책 엔진 결정 출력:

```
인덱싱 정책 결정 예시:
- SECRET + 온프레 스토리지 → 온프레 Vectorless 인덱싱만 허용, 온프레 LLM 전용
- CONFIDENTIAL + KR 관할 → 로컬 Vector + Vectorless 이중 인덱싱, 온프레/KR-클라우드 LLM만 허용
- INTERNAL + 참조빈도 높음 → 즉시 Vector 인덱싱, 클라우드 LLM 허용
- OPEN + 참조빈도 낮음 → 배치 Vectorless 선처리 후 백그라운드 Vector 인덱싱
```

**[0040] 이벤트 우선순위 증분 인덱싱 큐 (Priority-based Incremental Indexing Queue)** — 핵심 발명 포인트 ②

단순 FIFO 처리를 지양하고, 아래 스코어링 함수로 인덱싱 우선순위를 산정한다.

```
Priority_Score = w1 × QueryFrequency + w2 × SecurityWeight 
               + w3 × RecencyWeight + w4 × SizeInverseWeight

- QueryFrequency: 최근 30일 해당 문서 관련 질의 횟수 (정규화)
- SecurityWeight: 보안 등급별 가중치 (SECRET=1.0, CONFIDENTIAL=0.8, ...)
- RecencyWeight: 이벤트 발생 후 경과 시간의 역수 (최신일수록 높음)
- SizeInverseWeight: 문서 크기의 역수 (소형 문서 우선 처리로 빠른 서비스 반영)
```

실시간/배치 혼합 처리 전략:
- Priority_Score ≥ Threshold_High: 즉시 인덱싱 (동기 처리)
- Threshold_Low ≤ Priority_Score < Threshold_High: 준실시간 큐 처리
- Priority_Score < Threshold_Low: 배치 스케줄 인덱싱

**[0050] Vector + Vectorless 하이브리드 인덱스 전략** — 핵심 발명 포인트 ③

동일 문서에 대해 두 가지 인덱스를 병행 운용하며 이벤트에 따라 동적으로 전환한다.

```
Phase 1 (즉시 서비스):
  문서 이벤트 수신 → Vectorless 인덱스 빠르게 생성 → 즉시 질의 가능 상태

Phase 2 (품질 향상):
  백그라운드에서 임베딩 모델로 Vector 인덱스 생성
  → Vector 인덱스 완성 후 질의 라우터에 등록

Phase 3 (동적 전환):
  질의 패턴 분석 → 정확도 우선 질의: Vector 인덱스 사용
                 → 구조/페이지 참조 질의: Vectorless 인덱스 사용
                 → 복합 질의: 양쪽 결과 앙상블

이벤트 기반 인덱스 갱신 정책:
  UPDATE 이벤트 + 소규모 변경: Vectorless만 재생성 (빠른 반영)
  UPDATE 이벤트 + 대규모 변경: Vector + Vectorless 전체 재인덱싱
  DELETE 이벤트: 양쪽 인덱스 폐기, 글로벌 라우터에서 제거
```

**[0060] 글로벌 인덱스/라우터 (Global Index Router)** — 핵심 발명 포인트 ④

중앙 컨트롤 플레인의 핵심 컴포넌트로, 문서 원본이나 임베딩 벡터를 보유하지 않으며 다음 정보만 관리한다.

```
글로벌 라우팅 테이블 구조:
{
  document_id: "aws-s3-prod/path/doc.pdf",
  storage_location: "aws-s3-prod",
  agent_endpoint: "https://agent.aws-prod.internal:8080",
  index_status: {
    vectorless: { ready: true, version: 3, updated_at: "..." },
    vector: { ready: true, version: 2, updated_at: "...", model: "bge-m3" }
  },
  policy: {
    allowed_llm: ["on-premise", "aws-bedrock"],
    allowed_query_channels: ["browser", "mcp"],
    data_jurisdiction: "KR"
  }
}
```

질의 시 쿼리 플랜 생성:
- 사용자 권한 + 문서 정책 교차 검증
- 접근 가능한 스토리지 에이전트 목록 선별
- Vector/Vectorless 우선순위 결정
- 분산 질의 실행 후 결과 통합 (Federated Query)

**[0070] 멀티 LLM 오케스트레이터 (Multi-LLM Orchestrator)** — 핵심 발명 포인트 ⑤

질의 컨텍스트 기반으로 LLM을 동적 선택한다.

```
LLM 선택 결정 매트릭스:
┌─────────────────┬──────────────────┬─────────────────────────┐
│ 질의 보안 맥락  │ 문서 보안 등급   │ 선택 LLM                │
├─────────────────┼──────────────────┼─────────────────────────┤
│ 내부망 접속     │ SECRET           │ 온프레 오픈소스 LLM     │
│ 내부망 접속     │ CONFIDENTIAL     │ 온프레 or 국내 클라우드  │
│ 외부망 접속     │ INTERNAL 이하    │ 상용 클라우드 LLM        │
│ MCP 채널        │ OPEN             │ 고성능 상용 LLM          │
└─────────────────┴──────────────────┴─────────────────────────┘

채널별 응답 형식 자동 조정:
- Browser: HTML 렌더링 가능 마크다운, 인용 링크 포함
- Desktop App: 구조화 JSON + 문서 미리보기 메타데이터
- MCP: Tool-call 형식 JSON 응답
- A2A (Agent-to-Agent): 표준화된 에이전트 프로토콜 형식
```

### 동작 방법

**[0080] 문서 이벤트 처리 흐름**

```
Step 1: 스토리지 이벤트 감지
  → 각 스토리지 네이티브 이벤트 시스템이 로컬 에이전트에 이벤트 전달

Step 2: 메타데이터 추출 및 이벤트 허브 전송
  → 에이전트가 문서 메타데이터 추출 후 중앙 이벤트 허브로 요약 이벤트 전송
  → 문서 원본 콘텐츠는 스토리지에서 이탈하지 않음

Step 3: 정책 엔진 판단
  → 보안 등급, 규제, 참조 빈도 등 종합 분석
  → 인덱싱 방식(Vector/Vectorless/이중), 인덱싱 위치, 허용 LLM 결정

Step 4: 우선순위 큐 등록 및 인덱싱 지시
  → Priority_Score 산정 후 큐에 등록
  → 우선순위에 따라 해당 스토리지 로컬 에이전트에 인덱싱 지시

Step 5: 로컬 인덱싱 수행
  → Vectorless 인덱스 우선 생성 (빠른 서비스 반영)
  → 백그라운드에서 Vector 인덱스 생성
  → 완료 후 글로벌 라우터에 인덱스 상태 업데이트

Step 6: 글로벌 라우터 테이블 갱신
  → 인덱스 준비 상태, 버전, 허용 정책 업데이트
```

**[0090] 사용자 질의 처리 흐름**

```
Step 1: 질의 수신
  → Desktop App / Browser / MCP / API 등 다양한 채널로 질의 수신

Step 2: 질의 분석
  → 질의 유형 분류: 사실 질의 / 절차 질의 / 정책 질의 / 요약 질의
  → 사용자 프로파일 확인: 조직, 권한 등급, 접속 경로(내부망/외부망)
  → 응답 채널 특성 파악: 응답 형식 결정

Step 3: 쿼리 플랜 생성
  → 글로벌 라우터에서 접근 가능한 인덱스 목록 조회
  → 사용자 권한 × 문서 정책 교차 검증으로 접근 가능 문서 필터링
  → Vector vs Vectorless 우선순위 결정
  → LLM 선택 (보안 맥락 + 문서 등급 기반)

Step 4: 분산 질의 실행
  → 선별된 스토리지 에이전트들에 병렬 질의 전송
  → 각 에이전트 로컬 인덱스에서 검색 수행 (문서 원본 기반)
  → 검색 결과(청크, 페이지, 메타데이터)만 중앙으로 반환

Step 5: LLM 생성
  → 선택된 LLM에 검색 결과 + 질의 전달
  → 채널별 형식으로 응답 생성
  → 인용 출처 포함 (스토리지 위치, 문서 버전, 페이지/섹션)

Step 6: 응답 전달 및 질의 로그 기록
  → 사용자에게 응답 전달
  → 질의 로그 기록 → 우선순위 스코어링에 반영
```

## 청구항 (Claims)

### 독립항

**청구항 1 (시스템 청구항)**

복수의 이기종 문서 스토리지로부터 문서를 중앙에 집중하지 않고 RAG/LLM 기반 문서 질의응답을 제공하는 비중앙화 분산 RAG/LLM 플랫폼에 있어서,

각 문서 스토리지에 배치되어 해당 스토리지에서 발생하는 문서 이벤트를 감지하고 문서 원본을 중앙으로 전송하지 않은 채 이벤트 메타데이터만을 추출하여 전송하는 로컬 인덱싱 에이전트;

상기 로컬 인덱싱 에이전트로부터 수신한 이벤트 메타데이터를 기반으로, 문서의 보안 등급, 규제 관할권, 조직 단위 및 과거 질의 로그를 종합하여 인덱싱 방식, 인덱싱 위치 및 허용 LLM 모델을 동적으로 결정하는 정책 엔진;

상기 정책 엔진의 결정에 따라 인덱싱 작업에 우선순위 점수를 부여하고, 상기 우선순위 점수에 따라 인덱싱 작업을 순서화하여 실행하는 우선순위 기반 증분 인덱싱 큐;

동일 문서에 대해 벡터 임베딩 기반 인덱스와 임베딩 없는 Vectorless 인덱스를 병행 생성하고, 이벤트 유형 및 질의 패턴에 따라 상기 두 인덱스의 생성·갱신·폐기 전략을 동적으로 결정하는 하이브리드 인덱싱 모듈;

문서 원본 및 임베딩 벡터를 보유하지 않고 각 스토리지의 인덱스 위치, 인덱스 상태 및 접근 정책 정보만을 관리하며, 사용자 질의 시 접근 가능한 인덱스를 선별하여 분산 질의 계획을 생성하는 글로벌 인덱스 라우터; 및

사용자 질의의 유형, 사용자 권한 등급, 접속 채널 및 문서 보안 등급을 복합적으로 분석하여 상용 LLM 또는 온프레미스 오픈소스 LLM 중 하나 이상을 동적으로 선택하고, 접속 채널별로 상이한 응답 형식을 자동 적용하는 멀티 LLM 오케스트레이터;

를 포함하는 비중앙화 분산 RAG/LLM 플랫폼.

**청구항 2 (방법 청구항)**

비중앙화 분산 RAG/LLM 플랫폼의 운용 방법에 있어서,

복수의 이기종 문서 스토리지에 배치된 로컬 인덱싱 에이전트가 해당 스토리지에서 발생하는 문서의 생성, 수정 또는 삭제 이벤트를 감지하고, 문서 원본 콘텐츠를 스토리지 외부로 전송하지 않으면서 이벤트 메타데이터만을 중앙 이벤트 허브에 전송하는 이벤트 감지 단계;

정책 엔진이 상기 이벤트 메타데이터에 포함된 보안 등급, 규제 관할권, 조직 단위 및 과거 질의 로그를 종합하여 인덱싱 방식, 인덱싱 위치 및 허용 LLM을 결정하는 정책 결정 단계;

우선순위 기반 증분 인덱싱 큐가 문서의 질의 빈도, 보안 가중치, 이벤트 최신성 및 문서 크기의 역수를 포함하는 스코어링 함수에 따라 인덱싱 우선순위 점수를 산정하고, 상기 우선순위 점수에 따라 인덱싱 작업을 순서화하는 우선순위 산정 단계;

하이브리드 인덱싱 모듈이 Vectorless 인덱스를 먼저 생성하여 즉시 질의 가능 상태를 확보한 후, 백그라운드에서 벡터 임베딩 기반 인덱스를 생성하며, 이벤트 유형 및 변경 규모에 따라 인덱스 갱신 범위를 결정하는 하이브리드 인덱싱 단계;

글로벌 인덱스 라우터가 사용자 질의 수신 시 사용자 권한과 문서 접근 정책을 교차 검증하여 접근 가능한 인덱스를 선별하고, 분산 질의 계획을 생성하여 해당 스토리지 에이전트들에 병렬 질의를 전송하는 분산 질의 단계; 및

멀티 LLM 오케스트레이터가 질의 유형, 사용자 권한, 접속 채널 및 문서 보안 등급에 따라 LLM을 동적 선택하고, 접속 채널에 맞는 형식으로 응답을 생성하여 반환하는 LLM 오케스트레이션 단계;

를 포함하는 비중앙화 분산 RAG/LLM 플랫폼 운용 방법.

### 종속항

상기 정책 엔진은, 보안 등급이 최고 수준인 문서에 대해 Vectorless 인덱싱만을 허용하고 온프레미스 배포 LLM만을 사용하도록 제한하는 보안 격리 정책을 적용하는 것을 특징으로 하는 비중앙화 분산 RAG/LLM 플랫폼 또는 그 운용 방법.

상기 우선순위 기반 증분 인덱싱 큐는, 우선순위 점수에 따라 즉시 동기 인덱싱, 준실시간 큐 인덱싱, 배치 스케줄 인덱싱의 세 가지 처리 경로를 동적으로 선택하는 것을 특징으로 하는 비중앙화 분산 RAG/LLM 플랫폼 또는 그 운용 방법.

**청구항 5** (청구항 1 또는 2에 종속)

상기 멀티 LLM 오케스트레이터는, 접속 채널이 MCP(Model Context Protocol)인 경우 Tool-call 형식의 JSON 응답을 생성하고, 브라우저 채널인 경우 인용 링크가 포함된 마크다운 형식으로 응답을 생성하며, A2A(Agent-to-Agent) 채널인 경우 표준화된 에이전트 프로토콜 형식으로 응답을 생성하는 것을 특징으로 하는 비중앙화 분산 RAG/LLM 플랫폼 또는 그 운용 방법.

**청구항 6** (청구항 1 또는 2에 종속)

상기 글로벌 인덱스 라우터는, 사용자 질의에 대한 쿼리 플랜 생성 시 접근 가능한 복수의 스토리지 에이전트에 병렬 질의를 전송하고, 각 에이전트로부터 검색 결과만을 수집하여 통합 순위화(Federated Ranking)를 수행하는 것을 특징으로 하는 비중앙화 분산 RAG/LLM 플랫폼 또는 그 운용 방법.
